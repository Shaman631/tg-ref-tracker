# Промт для создания трекера реферальных ссылок Telegram на Laravel

## ПРОМТ

Ты senior Laravel-разработчик. Собери production-ready сервис **«Трекер подписчиков по
реферальным (пригласительным) ссылкам Telegram»** на Laravel. Пиши код сразу, не задавай
уточняющих вопросов по мелочам — все решения описаны ниже.

### Референс

В этом же репозитории уже есть рабочая реализация на чистом PHP — **изучи её перед
работой**, там уже решены все тонкости:

- `lib.php` — Bot API, состояние, подсчёт прироста, отчёт;
- `worker.php` — демон: команды Telegram + контроль времени;
- `index.php` — веб-страница управления с телефона;
- `python/tg_ref.py` — более ранняя версия на Python (логика идентична).

Нужна та же функциональность, но идиоматично на Laravel.

### Что делает сервис

Каждый вечер в заданное время (по умолчанию 21:00, TZ Europe/Samara) для каждого канала
создаётся **новая пригласительная ссылка**. Telegram сам считает, сколько людей по ней
пришло (`join_count`), бот присылает отчёт в Telegram. Управление — с телефона: кнопка на
веб-странице и/или команды в боте.

Пример отчёта:

```
📊 Реферальные ссылки — 2026-11-09

@my_channel
• Ссылка: https://t.me/+AbCdEf
• Пришло по ссылке сегодня: 12 (всего по ссылке: 12)
• Подписчиков в канале: 1543

Итого за день: +12 подписчиков по ссылкам
```

### Стек и ограничения

- Laravel 11/12, PHP 8.2+.
- **Никаких дополнительных composer-пакетах** — только то, что уже есть в Laravel
  (`illuminate/*`, `symfony/http-client`). Не тащить Telegram-SDK, не использовать Guzzle
  напрямую, не ставить отдельные пакеты под cron/очереди.
- Секреты — только через `.env` → `config/`. Токен бота не должен попадать в репозиторий
  (`.env` в `.gitignore`, рядом лежит `.env.example`).
- **Без системного cron.** Расписание реализовать так, чтобы процесс сам следил за
  временем: либо `schedule:work`, либо внутренняя проверка времени в long-running
  artisan-команде. Обязательно опиши в README, как это запускается в контейнере.

### Архитектура

**1. Миграции** (используй `Schema::create`, без raw SQL):

- `tg_links`: `id`, `chat_id` (string), `invite_link` (unique), `link_name`, `date`
  (YYYY-MM-DD), `join_count` (int, default 0), `member_count` (nullable), `created_at`,
  `updated_at`.
- `tg_daily_stats`: `id`, `date`, `chat_id`, `new_joins`, `total_joins`, `member_count`,
  `member_delta` — уникальный индекс (`date`, `chat_id`).
- `tg_job_runs`: `id`, `date` (unique), `links_created_at`, `report_sent_at`, `status`,
  `last_error`.

**2. Конфиг** `config/telegram.php` — значения из env:

| env | смысл | пример |
|---|---|---|
| `TG_BOT_TOKEN` | токен BotFather | `123:AA...` |
| `TG_CHAT_ID` | чат для отчётов | `123456789` |
| `TG_CHANNELS` | каналы через запятую | `@chan1,@chan2` |
| `TG_SCHEDULE_TIME` | время задачи | `21:00` |
| `TG_TIMEZONE` | часовой пояс | `Europe/Samara` |
| `TG_WEB_KEY` | ключ веб-страницы (необязательно) | — |
| `TG_PUBLIC_URL` | публичный URL сервиса (для команды `/webkey`) | `https://x.onrender.com` |
| `TG_STATE_BACKUP` | чат для бэкапа состояния (необязательно) | — |

**3. Сервисы** (в `app/Services/`):

- `TelegramService` — единственное место, где ходим в Bot API. Метод
  `call(string $method, array $params = []): array` поверх `Http::asForm()->timeout(90)`.
  Бросать `TelegramException` с текстом `description` из ответа.
- `ReferralLinkService` — создание ссылок дня, чтение статистики, подсчёт дельты.
- `ReportService` — сборка текста отчёта и отправка.
- `ScheduleService` — решение «пора ли выполнять задачу».

**4. Artisan-команды** (`app/Console/Commands/`):

- `telegram:bot` — long-running: слушает `getUpdates` и следит за расписанием;
- `telegram:daily` — один полный цикл (ссылки → статистика → отчёт), `--force` — даже
  если отчёт за день уже уходил;
- `telegram:stats` — снять статистику, без отправки; `--send` — отправить;
- `telegram:links` — показать ссылки дня;
- `telegram:setup` — мастер настройки: токен вводится со скрытием (`hidden()` / `secret()`),
  каналы через запятую, chat_id определяется сам по команде `/start`;
- `telegram:health` — диагностика: токен настроен, каналы, расписание, время последнего
  отчёта, живость процесса;
- `telegram:backup` — сохранить состояние в Telegram-чат файлом (`sendDocument`) и
  восстановить из него (`telegram:restore`).

**5. HTTP** (`routes/web.php`):

| Маршрут | Назначение |
|---|---|
| `GET /health` | JSON для health-check Render: без авторизации, без утечки секретов |
| `GET /` | мобильная страница управления (Blade) с одной кнопкой |
| `POST /api/run` | выполнить полный цикл прямо сейчас, вернуть отчёт в JSON |
| `GET /api/links` | ссылки дня в JSON |
| `GET /api/status` | сводка в JSON |

Ключ доступа: query-параметр `?key=...` (запоминать в cookie) либо заголовок. Если
`TG_WEB_KEY` не задан — детерминированно выводить ключ из токена:
`substr(hash('sha256', 'tg-ref-web:'.$token), 0, 32)` — тогда он **не меняется** между
редеплоями и закладка в телефоне остаётся рабочей.

**6. Blade-страница** (`resources/views/...`): мобильная вёрстка, одна большая кнопка
«Создать ссылки и прислать отчёт», вторая — «Ссылки дня», блок с ответом сервера и
информация о последнем отчёте. Страница должна нормально открываться с телефона.

### Логика подсчёта прироста (критично)

- Ссылка дня создаётся через `createChatInviteLink` с именем
  `ref_YYYYMMDD_<username>` (только `[A-Za-z0-9_-]`, максимум 32 символа).
- `getChatInviteLinkStats` возвращает **накопительный** `join_count` по этой ссылке, а не
  за день.
- Поэтому: хранить последний увиденный `join_count` по ссылке, дельта =
  `max(0, join_count - сохранённый)`, и **накапливать** дельту в `tg_daily_stats` за дату.
  Повторный запуск в тот же день должен **прибавлять** прирост, а не перезаписывать и не
  задваивать. Это самая частая ошибка — проверь её тестом.
- Итог дня = сумма накопленных дельт по каналам.
- Общее число подписчиков канала — `getChatMemberCount` (для контекста, не обязательно).
- Отчёт — `sendMessage` с `parse_mode=HTML` в `TG_CHAT_ID`.
- **Защита от дублей:** `tg_job_runs.report_sent_at` — если за дату отчёт уже уходил,
  повторно не отправлять (кроме `--force`). При этом статистику можно обновить.

### Расписание без крона

- В `telegram:bot` в цикле: `getUpdates(timeout=20)` → обработка команд → проверка
  «пора ли» → пауза.
- «Пора ли»: текущее время в `TG_TIMEZONE` >= `TG_SCHEDULE_TIME` **и** за сегодня в
  `tg_job_runs` нет `report_sent_at`.
- Догон: если за вчера были ссылки, но нет `report_sent_at` — сначала отчёт за вчера,
  потом за сегодня.
- **Роут `/health` тоже проверяет расписание.** Значит, дешёвый внешний пингер
  (UptimeRobot, раз в 5 минут) не только не даёт сервису уснуть, но и запускает
  вечернюю задачу вовремя. Это обязательное поведение, а не оптимизация.

### Команды бота (в Telegram)

`/start` — подсказка + ваш `chat_id`; `/daily` — полный цикл; `/links` — ссылки дня;
/`/status` — расписание, каналы, время последнего отчёта; `/webkey` — ключ доступа и
готовая ссылка на страницу управления.

При `/daily` отчёт уходит и в `TG_CHAT_ID`, и в чат, откуда пришла команда. **Не дублировать**,
если это один и тот же чат.

### Критичные детали (проверено на практике)

1. **Telegram не будит уснувший сервис.** Пока Render-сервис спит (бесплатный план
   засыпает через 15 минут тишины), бот не ответит ни на что, а команды будут копиться.
   Спасает пингер `/health` раз в 5 минут.
2. **Один потребитель `getUpdates` на бота.** Два процесса с long polling будут конфликтовать
   (Telegram отдаёт 409). В деплое должен быть ровно один такой процесс.
3. `join_count` — счётчик ссылки, а не «сколько пришло сегодня». Дневная деelta считается
   разницей снапшотов.
4. Часть подписчиков приходит не по ссылке (прямая ссылка на канал, поиск) — их не видно
   в `join_count`, но видно в `getChatMemberCount`. Это ограничение Telegram.
5. На бесплатном Render файловая система эфемерна: состояние в БД, а для переживания
   редеплоя — бэкап в Telegram-чат файлом (`sendDocument` + `getFile` для восстановления).
   Предусмотри и то и другое.
6. Имя ссылки (`name`) — только `[A-Za-z0-9_-]`, до 32 символов, иначе Telegram отвергнет.
7. `getChatInviteLinkStats` работает только для ссылки, созданной ботом-админом канала.
   Бот должен быть администратором канала с правом **«Приглашать пользователей»**
   (`can_invite_users`). Проверяй это в `telegram:health` и `telegram:setup`.

### Тесты

PHPUnit или Pest, `Http::fake()` для Telegram API. Обязательные кейсы:

1. Создание ссылки дня и сохранение в `tg_links`.
2. Дельта: снапшот 0 → 10 → повторный запуск даёт 10 (не 0 и не 20).
3. Второй запуск в тот же день **не отправляет** второй отчёт (защита от дублей).
4. Отчёт содержит ссылку, прирост по каждому каналу и итог.
5. `GET /health` → 200 и JSON без токена в ответе.
6. `GET /` без ключа → 401/403; с ключом → 200.
7. `POST /api/run` → 200 и отчёт в JSON.
8. Ключ доступа стабилен: одинаковый токен → одинаковый ключ; заданный `TG_WEB_KEY`
   имеет приоритет.

### Деплой

- `Dockerfile` на официальном образе PHP 8.3: два процесса в одном контейнере —
  веб-сервер и `php artisan telegram:bot` (см. референс `Dockerfile`). Не используй
  `php artisan schedule:work`, если в контейнере уже живёт long-running процесс.
- `render.yaml` (Blueprint): web service, `healthCheckPath: /health`, план `free`,
  переменные окружения через `sync: false`.
- В README обязательно предупреди: на бесплатном тарифе сервис засыпает через 15 минут
  без запросов, и без пингера `/health` бот не будет отвечать, а задача в 21:00 не
  сработает. Опиши настройку UptimeRobot (интервал 5 минут).

1. `php artisan test` — все тесты зелёные.
